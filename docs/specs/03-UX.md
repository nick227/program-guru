# UX — Pages, journeys, and precise interaction rules

**Status:** Authoritative P1 baseline · **Authority:** screens, screen order, focus, copy, transitions, empty/error/loading behavior. UI implementation mechanics belong in `04-UI.md`.

## 1. Unbreakable UX principles

1. **One focus per view:** One meaningful decision, task, or primary action. Avoid simultaneous setup forms.
2. **Low cognition:** Minimal words, limited well-labeled choices, no hidden critical actions.
3. **Buttons before typing:** Seed subjects, counts, schedules, metrics, and media sources; text fields only when necessary.
4. **Best realistic defaults:** Suggest editable title, description, targets, frequency, format, timezone; never invent a fact or claim it is verified.
5. **Progressive disclosure:** Rich options remain available inline or through clearly named Add/More actions; avoid separate Edit modes for basic fields.
6. **Show the object, not the setup checklist:** Workspace reflects real Program and Activity content, not eight config tiles.
7. **Context preservation:** Picker, media studio, instruction editor, detail drawer return to originating page and scroll/day selection.
8. **Nonlinear creation:** Autosave draft; resume/edit any stage; publishing is deliberate.
9. **Personal first:** Today's task and private results ahead of social/community counts.
10. **No mandatory social action:** Finish an Activity without recording or posting; never block completion behind instruction playback.
11. **Automatic first, adjustable after:** The system proposes a schedule; manual calendar editing is always available and never required.
12. **Simple by default, advanced on demand:** Customization stays behind `Edit`, `More`, and `Customize Copy`.

Copy: short, direct, professional. Use `Add Program`, `Add Activity`, `Start`, `Pause`, `Resume`, `Finish`, `Preview & Publish`, `Save`, `Join`, `Unlock`, `Record`, `Upload`. Avoid motivational slogans, metaphorical button labels, or overlong explainer paragraphs.

## 2. Navigation / destinations

**No primary navigation bar is used.** A consistent app header remains visible on every page and spans the viewport, with responsive gutters. The signed-in app opens on the user's monthly Calendar, with `+ Program`, `+ Activity`, and a top-right avatar/user widget showing notification indicator. Calendar can switch between Day, Week, Month, and Year. The Calendar is the full-width home surface, aligned to the header gutters; it gives month cells and week columns room for readable Activity tiles. Other pages may use a focused content width. Today is unmistakable whether or not it is selected. Activity tiles stay minimal and visually quiet: they show thumbnail/icon, title, optional source Program, available group participant avatars/unread dot, subtle visual completion styling (with status exposed accessibly via `aria-label`, never as visible status badges), and an inline quick-complete button for planned items—with no `"More actions"` overflow menus. Do not add a separate Today summary or Reminders panel beneath the Calendar. User widget opens Profile / My Programs / My Media / Notifications / Settings. Secondary screens reachable via contextual buttons, breadcrumbs/back, or panels.

## 3. Add a Program

Finding a starting point and creating a Program are one continuous experience. A selected published Program is a prefilled starting point, not a separate join-or-create decision. The user's Program is a private, independently editable instance; the source remains unchanged and its source-version reference is retained for attribution and future update options.

1. **Type:** First ask “What kind of Program?” Show the available Program Types. Selecting one classifies a new Program and filters starting points to that type.
2. **Name or choose a starting point:** Ask “What is your Program?” The title field is for naming a new Program. Beneath it, show at most **five suggested starting points** for the chosen type (most popular within the type and focus, widening to the type, then all), each a single `Use as starting point` action, plus a distinct `Browse Program Library` action. The library is a full-screen, route-addressable browser (`…/browse`) layered over the still-mounted form, with search, sort, creator and focus filters; Back closes it without losing entered values. Selecting a source Program (from the suggestions or the library) fills the title field and selects its structure; changing the title must not discard that structure. The user can instead continue with a blank Program. The chosen type is kept in the URL.
3. **Customize:** Create a private editable Program instance and open its workspace. A copied starting point includes reusable Activities, instructions, metrics, and suggested schedule where access permits; changes affect only the personal copy. A new title starts with a blank structure. The user can continue editing the title, Activities, instructions, duration, and schedule.
4. **Add to Calendar:** Once customized, save the personal Program instance and place its schedule on the user's calendar without publishing it as a reusable storefront Program.

Do not split discovery and creation into separate mandatory pages. Keep the Add Program view focused on Program Type and a clear blank-creation path. Suggestions are a five-item shortcut, never a catalog or a second editor; search and filters live only in the library browser. The selected starting point is summarized on the form and can be removed before continuing. Suggestions and the library use one discovery source and the same card.

The existing contracts create/copy a private draft with provenance, customize it, publish a private snapshot, and enroll that version. `Add to Calendar` performs the private publish and enrollment in sequence; show errors and allow retry if one succeeds without the other. Never change the source Program's visibility or content.

## 4. Locked Program Workspace layout (do not reinterpret)

**Approved 2026-11-10: three steps.** The Workspace has a persistent header (back link, inline Program name with autosave and conflict handling) and a stepper (`Details` → `Activities` → `Publish & Share`). Each step is one page section with `Back` / `Continue` at the bottom; a step is reachable directly at `/programs/:id/workspace/:step`.

```text
← My Programs
My Strength Program                     [inline editable, autosaved]
(1 Details) ── (2 Activities) ── (3 Publish & Share)
──────────────────────────────────────────────────
1 Details     Workout · Strength · 8 weeks
              [cover tray]  Description [autosaved]  Duration [1 wk|2 wk|4 wk|8 wk|Ongoing]
2 Activities  Activities · 3 activities · 8 weeks          [Browse Library]
              [ Squats   frequency · duration · media · N days scheduled ]  [Edit]
              [ Leg Raises ... ]
              [ New Activity: title · description · frequency · duration · media · Add to Program ]
3 Publish     summary · visibility [Public|Link only|Private] · groups and invites
              publish-check issues inline            [Back]  [ ] Start now  [Publish Program]
```

- The Program cover uses the shared media tray (`04-UI.md` §4a): one preview tile with inline remove and one add/replace tile, no separate upload or library buttons. It sits on the Details step; it is not a hero.
- The Program name stays editable in the header on every step. Preserve autosave, conflict handling, automatic scheduling, and manual placement adjustment.
- Frequency and duration belong to each Activity (07 §7, 08 §2): every Activity row, and the inline New Activity form, has its own frequency and duration controls. Program duration is chosen on Details.
- `program days` counts days with at least one placement. It is never labeled “sessions”: each placed Activity has its own Calendar Item and Activity Sessions.
- Each Activity row opens an inline editor and links to Activity Detail/Editor. `Browse Library` uses the picker and returns to this step. With no Activities, one empty state `No activities yet` plus the inline New Activity form.
- `Publish` stays available on step 3; when publishing is blocked, the publish-check issues are listed inline and the summary still shows. Publishing keeps the Program's access mode as set in Creator Studio.
- Program detail (`/programs/:id`) may offer its owner the same controls inline (details, cover, duration, visibility, Activity rows). It reuses the Workspace's components and does not replace the Workspace.
- Do **not** add an 8-item setup grid or separate Pricing/Calendar steps to the Workspace.

## 5. Calendar: first-stop daily experience

Top: month heading/navigation; controls `+ Program`, `+ Activity`; user avatar with unread badge. Default shows the **current month** with today highlighted, in the user's timezone; day, week, and year views are one button away. Activity tiles show thumbnail/icon, title, optional origin Program, Day-view local time if set, collaborator avatar(s) or unread indicator when meaningful, and quiet visual completion styling (no visible status badges or `"More actions"` overflow menus; do not reintroduce them in future refactors). A tap opens the **dated occurrence**, not the reusable Activity editor. Choosing a date in Week, Month or Year opens Day view for that date; today is marked with `aria-current="date"` and a distinct style whether or not it is selected.

**First use:** an empty week, one line `Nothing scheduled this week`, a prominent `Browse Programs`, and a secondary `Add Activity`. Any later empty week or day uses the same copy and actions.

**Add Program:** browse/preview → (Unlock if needed) → `Start Program`, which schedules the Program from today in one action and stays on the Program page (`13` §4). No date picker, preview, confirmation or reminder prompt on the Program page. A group invitation's start date still applies. **Add Activity:** picker → select target date/time (default current selected date; time optional) → `Does not repeat` by default, or Daily/Weekdays/Weekly/Custom → confirm.

**Adjusting:** a tile's time can be changed inline in Day view, clearing it moves the item to Any time, and items can be dragged between hourly/Any time slots; preserve user-specific adjustments. Individual Calendar tiles omit overflow menus (`More actions` / `Remove from Calendar`); Program-level removal (`Remove from Calendar`) lives on Program Detail, while individual item cancellation APIs remain preserved underneath.

**Conflicts:** overlapping Activities are allowed. Timed items at the same local time are marked on both tiles, with one-tap `Move` offering the next open slot. Never block scheduling.

**Responsive:** desktop has the week grid + optional side panel; mobile shows a week strip above the selected day's list and a detail sheet. Keyboard alternative for all drag actions (Move button with date dialog).

## 6. Participant Activity

1. **Activity Hero:** restrained photographic banner using actual Activity media, title, Program/day/date, description, status and compact real progress. When the occurrence has a scheduled place, one quiet line in the Hero shows the Place name and city, linking to its details (`08-ACTIVITIES.md` §2a) and a change/clear control for the owner; this is part of the Hero, not a new row. Without an image use a compact text identity, not a placeholder banner.
2. **Today's Activity:** instructions and one prominent context-aware action. Timed ready Activities lead with Start, simple Activities with Complete; active shows Complete and Pause, paused leads with Resume, completed offers Undo completion. Timer is secondary and shown only for timed/started sessions. Header and controls derive the same state. No duplicate upload action.
3. **My Metrics:** configured result inputs and real personal statistics (completion counts, streaks or progress only when supplied). Never prefill recorded values from targets. Omit it if there are neither inputs nor statistics. *(Approved 2026-11-10: these render inside the Today section, after its statistics and before the instructions, rather than as a separate row.)*
4. **Together:** actual group avatars, permitted completion states, recent shared completions/starts, reactions and group access. No inferred live presence or claims about private members. Group occurrence identity remains authoritative across Program versions. Omit for solo Activities.
5. **Related Media:** a single responsive gallery combining personal media across attempts, group shares and permitted public/Program media. All/Mine/Group/Public filters change the same gallery. Include attribution, viewing, direct uploads and processing/retry states. Owner menus provide deletion and sharing/revocation. No Media Library workflow or dedicated History section; preserve historical records and server authorization.


Instruction text is **embedded**, and instruction media appears in Related Media: 1 instruction with a primary video surfaces naturally as helpful thumbnail/inline selected content; multiple instructions accessible by swiping/next or expanding within the activity, no obligatory “Read instructions” screen. These rows are the whole page; do not add, reorder, or tab them. The one addition is an optional privacy-safe community aggregate line after Related Media, shown only when the server supplies it. Do not force media into a huge hero by default; user results and completion remain first. Photo/video is optional and not a prerequisite to `Finish`.

### Session state interaction

`READY -> ACTIVE -> PAUSED -> ACTIVE`, `ACTIVE|PAUSED -> FINISHED`, optional `ABANDONED` with confirmation. `Finish` records effective active time, never pause time, saves pending results, and **returns to the same calendar week and date** with completion visible and `Undo` available. Reopening a finished occurrence shows its completed status and `Undo completion`. Starting does not automatically mark Activity complete; completion is explicit. If the user completes without starting, offer quick `Mark finished` with explicit result saved as manual duration/unknown time rather than synthesizing a measured duration. Restart after Finished should create a **new session attempt**, not erase history.

### Metrics controls

Use compact `− value +` for counts, one-tap `Start Timer` for duration, toggles for yes/no, text only for notes or custom inputs. Prefill *suggested target*, never silently copy it into actual result as verified. If result was modified, saving is immediate/explicit by stable affordance; undo available. Show unit and metric label. Do not show irrelevant metrics.

## 7. Activity and Instruction Builder

**Add Activity is one create-or-start experience**, not a suggestion catalog with creation hidden behind it. Lead with the user's own Activity title and the minimum required classification. Summary and instructions are optional. Keep the primary action available for a new Activity without requiring a suggestion selection. Existing Activities are optional starting points: up to five suggestions and a `Browse Activity Library` action that opens the shared library browser (see `08-ACTIVITIES.md` §6).

Use the same Activity basics form in both Calendar and Program contexts: title, category, optional summary, and optional instruction. Continue in context: create a private Activity and place it on the chosen Calendar date, or create it and add it to the current Program. Creation and placement errors remain visible, preserve entered content, and allow retry. The Calendar retains its selected date and return destination.

After the basics, offer `+ Media` / `+ Metrics` / `+ Tools` / `+ Instruction` as optional enrichment. Save Private is the default; Publish is separate and deliberate. A user can create an Activity with only a title and category, then enrich it later.

**Instruction mini-builder:** (1) brief guidance/name → (2) optionally attach media/metrics/tools with same controls → (3) Done/Add another. Reusable component patterns; no forced 14-step flow. A one-instruction Activity can be effectively a video; no extra navigation for basic playback. Instructions are ordered, without recursively nested instructions.

**Customizing:** Select seeded/public Activity → `Use as is` or `Customize Copy`; attempting to edit an Activity you do not own always creates a personal copy. The copy starts private with source attribution; the original never changes. Return to the original Program with the selected activity placed.

## 8. Media Studio and engagement

Entry button `Add Media` opens three broad actions: `Library`, `Upload`, `Record`. Library distinguishes **My Media** and **Platform Library** without separate mandatory tabs; search and filters are available. Record: camera preview, context-specific prompt, record, review/retake, choose audience; save **Private** by default; return to originating item. Camera/mic consent only on start; if denied, offer `Upload instead`.

Media viewer: tap thumb → play → swipe/next or desktop arrows → creator credit. Public media shows compact like/view metadata. Group-shared media shows its comments. The currently selected Program creator's eligible instructional media sorts first. Comments exist only on group-shared media in P1.

## 9. Collaboration behavior

In solo activity, hide collaboration rows. Group activity row shows members, statuses, and completion reactions. Finishing an item shares only the approved completion signal under group policy; never implicitly shares exact measurements or media. Joining a group states plainly that completion will be visible to members and that this can be turned off. Reactions target permitted completion events. Comments target group-shared media. There is no general chat and no `Live` control in P1.

## 9a. Reminders and achievements

**Reminders:** in-app notifications are on by default. The daily email is optional, off until the user opts in, sent at their chosen local time (default 08:00), and only on days with planned items. Every email has a one-click unsubscribe.

**Achievements:** earned quietly from actual completions and shown on the Finish return as a small confirmation, then on the user's profile. They are private until the user shares them. Never use guilt, streak, or comparison language.

## 10. Cross-page states

| State | UI behavior |
|---|---|
| Initial startup | Restrained branded splash only while the app actually initializes, then the weekly Calendar (`13` §8) |
| Loading | Skeleton matching actual row/grid; buttons avoid accidental duplicate submissions |
| Empty | One sentence maximum and a single useful action; e.g. `No activities yet` + `Add Activity` |
| Validation | Field-local and actionable; only block essential missing data |
| Save pending | Small `Saving…` near edited area; do not block page; retry error visible |
| Save conflict | Preserve local edits, explain newer version, offer reload/compare |
| No connection | Show cached items where available; writes are disabled with a short explanation, not queued, in P1 |
| No camera access | `Upload instead` and short permission explanation |
| Unauthorized | Do not render locked media; return preview/request access |
| Archived content | Historical records visible; editing/publishing controls removed as appropriate |
| Session interrupted | On reopen offer `Resume`, `Finish`, or `Discard`, with recorded time intact |
| No collaborators | Remove collaborator and shared-media rows; no empty boxes |
| Payment pending | Show `Confirming payment…`; grant access only after server verification |
| Subscription lapsed | Keep Calendar Items and history; locked instructions and media show `Renew` |
| Program update available | Small `Update available` prompt; nothing changes until accepted |
| Schedule conflict | Mark both tiles; offer one-tap `Move`; do not block |

## 11. Accessibility and mobile-first requirements

Minimum 44px touch targets for primary actions; meaningful focus outlines; visible labels for icon-only controls on hover/assistive tech; keyboard-operable grid/carousel/calendar; screen reader announcements for recording/session state and saved metrics; caption/transcript support for instructional video; do not autoplay with sound; respect reduced-motion; sufficient contrast; avoid public health/body comparisons or guilt-based copy.

## 12. Handoff checklist

Each implemented page must specify: entry action, origin context, main action, returned destination, empty/loading/error states, privacy gate, keyboard/mobile path. Screens must never invent additional persistent data fields without an authoritative domain contract.
