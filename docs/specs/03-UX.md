# UX — Pages, journeys, and precise interaction rules

**Status:** Authoritative P1 baseline · **Authority:** screens, screen order, focus, copy, transitions, empty/error/loading behavior. UI implementation mechanics belong in `04-UI.md`.

## 1. Unbreakable UX principles

1. **One focus per view:** One meaningful decision, task, or primary action. Avoid simultaneous setup forms.
2. **Low cognition:** Minimal words, limited well-labeled choices, no hidden critical actions.
3. **Buttons before typing:** Seed subjects, counts, schedules, metrics, and media sources; text fields only when necessary.
4. **Best realistic defaults:** Suggest editable title, description, targets, frequency, format, timezone; never invent a fact or claim it is verified.
5. **Progressive disclosure:** Rich options remain available inline or through clearly named Add/More actions; avoid separate Edit modes for basic fields.
6. **Show the object, not the setup checklist:** Workspace reflects real Program and Activity content, not eight config tiles.
7. **Context preservation:** Picker, media studio, instruction editor, detail drawer return to originating page and scroll/day selection.
8. **Nonlinear creation:** Autosave draft; resume/edit any stage; publishing is deliberate.
9. **Personal first:** Today's task and private results ahead of social/community counts.
10. **No mandatory social action:** Finish an Activity without recording or posting; never block completion behind instruction playback.
11. **Automatic first, adjustable after:** The system proposes a schedule; manual calendar editing is always available and never required.
12. **Simple by default, advanced on demand:** Customization stays behind `Edit`, `More`, and `Customize Copy`.

Copy: short, direct, professional. Use `Add Program`, `Add Activity`, `Start`, `Pause`, `Resume`, `Finish`, `Preview & Publish`, `Save`, `Join`, `Unlock`, `Record`, `Upload`. Avoid motivational slogans, metaphorical button labels, or overlong explainer paragraphs.

## 2. Navigation / destinations

**No primary navigation bar is used.** A consistent app header remains visible on every page and spans the viewport, with responsive gutters. The signed-in app opens on the user's monthly Calendar, with `+ Program`, `+ Activity`, and a top-right avatar/user widget showing notification indicator. Calendar can switch between Day, Week, Month, and Year. The Calendar is the full-width home surface, aligned to the header gutters; it gives month cells and week columns room for readable Activity tiles. Other pages may use a focused content width. Today is unmistakable whether or not it is selected. Activity tiles stay minimal and visually quiet: they show thumbnail/icon, title, optional source Program, available group participant avatars/unread dot, subtle visual completion styling (with status exposed accessibly via `aria-label`, never as visible status badges), and an inline quick-complete button for planned items—with no `"More actions"` overflow menus. Do not add a separate Today summary or Reminders panel beneath the Calendar. User widget opens Profile / My Programs / My Media / Notifications / Settings. Secondary screens reachable via contextual buttons, breadcrumbs/back, or panels.

## 2a. Home (revised 2026-11-15)

**Current Home:** the Home Agent alone. Its opening turn keeps the Continue/Today priority (§1.9) and shows each suggestion's image (Agent turn images, below); `Something else` opens every Agent flow. The Activity surfer and the Suggested card below it were **retired on 2026-11-15** (commit `1ebd3d0`); items 2 and 3 are kept only as the record of that design, and Home makes none of their requests. Activities are surfed through the Agent (`Explore Activities`, `Next Activity`).

*Retired design (record only):* Home got a person to a real, participation-ready Activity in one or two taps. Order, top to bottom:

1. **Today first** (§1.9). The Home Agent's opening turn keeps its Continue/Today priority and its choices (`Something else` opens every existing Agent flow). On Home it renders compactly.
2. **Activity surfer.** One prominent, media-led Activity with visible `Previous`/`Next` buttons, left/right arrow keys and horizontal swipe. Its position (`3 of 24`) is shown. Next and Previous are local: no request writes anything. Adjacent media is prefetched. Candidates, deduplicated by Activity: gatherings happening now → Opportunity Radar recommendations (with their first reason) → other upcoming public gatherings → varied catalog Activities (`12-SOCIAL.md` §5a). With a gathering, the card shows the real people and time; without one, no people. Each card names its creator (Follow when signed in and not already followed or self) and opens the creator's profile.
3. **Suggested** Program or Creator: the existing presentation card, so Program discovery and creator attribution stay on Home.

**Reschedule, not Move to tomorrow (2026-11-15).** Home's turn for an item scheduled today offers `Start now`, `Show my day`, **`Reschedule`** and `Something else`. Reschedule opens the shared Add to Schedule dialog in its reschedule mode: the item's date (today) and time preselected, past days disabled, `Move to <day>`. A recurring item must choose `This one` (default) or `This and future` (09 §4.8); a gathering item says that moving leaves the gathering (10 §9.6). It edits the existing item through `updateCalendarItem` with its `expectedUpdatedAt`; it never creates an item, and nothing moves without that confirmation. Recommended or unscheduled Activities offer `Add to Schedule` instead.

**Agent intents (approved 2026-11-15).** The intent menu keeps four Program/Activity intents apart; exploring never creates and creating never recommends:
- **Explore Activities** (was `Do something now`): the existing time → Domain → Activity flow.
- **Explore Programs** (was `Start a Program`): the existing focus → level → session-length matching of *existing* Programs, unchanged; its copy never says "new".
- **Create a Program**: Home's inline builder. First the Add Program form (`§3`; type, name, cover, description, optional starting point), then the Workspace's own title editor, stepper and three steps (`§4`, unchanged) in place on Home. `Browse Library` opens the Activity library picker over the Activities step and returns to it; the inline New Activity form creates custom Activities. The draft autosaves on the server; the builder's step and picker are saved with Home's conversation, so Back, Next and reload keep them. `Cancel` before the draft exists creates nothing; afterwards `Save draft & exit` leaves the draft resumable. Only the Publish step's explicit `Publish Program` publishes; Home then shows the published Program's preview. No Program Activity reordering.
- **Continue editing** (shown when the viewer has drafts): lists up to four drafts by title, plus `Create a new Program`; choosing one reopens the builder on its Activities step.
`Do something together`, `Continue where I left off` and `Find something to do` stay as they are.

**Agent turn images (2026-11-15).** Every Home Agent suggestion shows its card's best available media above the question, so surfing with `Another idea`, `Next Activity` or `Next creator` is visual: a Program's cover, an Activity's cover (else its resolved thumbnail), a creator's leading Program cover from already-loaded discovery with their avatar over it, a Calendar item's thumbnail; without media, the Domain's category art (11-MEDIA identity order). Tapping the image opens the preview. The next suggestion's image is warmed in advance; nothing extra is fetched.

**Show me: the inline Program overview (2026-11-15).** Every Agent turn that suggests a Program (opening, Explore Programs, Continue, Do something together's fallback, an enrolled Program's turn) offers one **`Show me`**, which replaces the former `Preview Program`; a turn never shows both. It opens the Program overview in place over the turn, without navigating, and selecting it never enrolls, schedules or changes progress. The overview shows the Program hero, title, creator (to their profile) and type · level; a short description; **Commitment** (duration, frequency, minutes a session) and **People** (the participant count, or `Fewer than 5 participants` under the minimum sample, 12 §10; followed participants' avatars; `including you` for a participant); then the viewer's own run when there is one (from the personal library: `N of M done` with a progress bar, and the next three upcoming Activities linking to their occurrences); then the **Activity plan** (the preview-safe outline, five rows, each Activity's first day shown once per day). Actions by state: enrolled `Continue` (the next occurrence); not enrolled `Start Program` (the existing join from today) and `Add to Schedule`; signed out `Add to Schedule` (asks to sign in); completed or owned, a `Completed` / `Created by you` note; always `Open Program Page`. Personal progress is never shown or invented for a viewer without a run. `Back` closes the overview and returns to the same turn, recommendation and history. Session, Creator and today's-schedule turns keep their `Show me` below the turn (who is in the session, the Creator's Programs, today's timeline). The 2026-11-15 removal of the Suggested card had left `Show me` with no visible result, which read as Home resetting.

**Participate** opens the focused Activity preview in place, creating nothing. Its actions use the existing operations only: **Join** (the gathering's repeat-safe join, reusing the viewer's compatible item; signed out: sign in to join), **Start** (reuses today's planned personal item of the same Activity when one exists, otherwise adds one for today, then opens inline participation), **Add to Schedule**, and Open Activity Page.

**Add to Schedule** is one shared button and dialog for Activities and Programs. For a Program it picks only a start date and starts the run through the existing join (`13` §4). It appears wherever Home offers an Activity: the surfer card, the focused preview (replacing Add to Today), and every Home Agent Activity suggestion beside `Start`/`Start now` and `Next Activity`. It opens a modal over the current view with the Calendar's date picker (start date; today preselected, past days disabled), an optional time, and **Repeat**: `Once` · `Daily` · `Weekly` (day chips, the start's weekday preselected) · `Monthly` (on the start date's day, clamped to short months). A repeating entry chooses how long: `Ongoing` · `For 2 weeks` · `For 1 month` · `For 3 months` · `Until a date` (Save waits for that date), with a one-line summary of what Save will do ("Every week on Mon, Wed · until Dec 14"). It maps onto the existing personal recurrence (09 §4.8: `DAILY`, `WEEKLY` with weekdays, `MONTHLY`, `untilDate`), managed afterwards on the Calendar with `This one` / `This and future`. One Save (`addCalendarItem`, one idempotency key per opening) adds one item or one recurrence however often it is pressed. Saving confirms with a toast and leaves the viewer where they were. Signed out, it asks to sign in. Back returns to the same surfer position, Agent step and history. While the Agent is past its opening turn, a preview or inline participation is open, or the day schedule is shown, the surfer is hidden.

## 2b. Activity participation, everywhere (approved 2026-11-15)

Every surface that shows an Activity (Home Agent suggestions and previews, Community cards and search results, the Activity preview drawer, the Activity page, Program Activity rows, the Calendar rail and Activity picker) uses **one** state resolver and **one** participation component, fed by `GET /activities/participation` (12 §10a). No surface derives these states itself.

**Your status** (signed in), in this precedence, with the other facts still shown beside it: **In progress** (a running or paused session) → **Scheduled** (a PLANNED item today or later: its date and time, and its recurrence, e.g. "Every week on Mon") → **Completed** ("Done 3 times · last Nov 2") → **Added before** ("Last added Oct 30") → **Not on your Calendar**. A scheduled Activity that was also completed reads "Scheduled Thu 7:30 AM · Done 3 times". Signed out, no personal status.

**People**, always visible, including zero: authorized avatars beside the count band ("0 participants", "Fewer than 5 participants", "12 participants"; "· including you"). Then shared activity when it exists: "2 doing it now", "4 going · Sat 9:00 AM".

**Actions** (the full component): `Resume` when in progress; otherwise `Start now` (reuses today's planned personal item). `Join` (or `Open`) when a joinable gathering exists. `Add to Schedule` always (another occurrence or recurrence is allowed). `Reschedule` for the next scheduled item, through the shared dialog's reschedule mode (`This one` / `This and future` for a recurring item, §2a). `Open Activity Page` is secondary and absent on the Activity page. Signed out, actions ask to sign in. The compact form (cards, rows, results) shows the status and people lines and one icon action: `Add to Schedule` when not scheduled, `Reschedule` when it is.

## 3. Add a Program

Finding a starting point and creating a Program are one continuous experience. A selected published Program is a prefilled starting point, not a separate join-or-create decision. The user's Program is a private, independently editable instance; the source remains unchanged and its source-version reference is retained for attribution and future update options.

1. **Type:** First ask “What kind of Program?” Show the available Program Types. Selecting one classifies a new Program and filters starting points to that type.
2. **Name or choose a starting point:** Ask “What is your Program?” The title field is for naming a new Program. Beneath it, show at most **five suggested starting points** for the chosen type (most popular within the type and focus, widening to the type, then all), each a single `Use as starting point` action, plus a distinct `Browse Program Library` action. The library is a full-screen, route-addressable browser (`…/browse`) layered over the still-mounted form, with search, sort, creator and focus filters; Back closes it without losing entered values. Selecting a source Program (from the suggestions or the library) fills the title field and selects its structure; changing the title must not discard that structure. The user can instead continue with a blank Program. The chosen type is kept in the URL.
3. **Customize:** Create a private editable Program instance and open its workspace. A copied starting point includes reusable Activities, instructions, metrics, and suggested schedule where access permits; changes affect only the personal copy. A new title starts with a blank structure. The user can continue editing the title, Activities, instructions, duration, and schedule.
4. **Add to Calendar:** Once customized, save the personal Program instance and place its schedule on the user's calendar without publishing it as a reusable storefront Program.

Do not split discovery and creation into separate mandatory pages. Keep the Add Program view focused on Program Type and a clear blank-creation path. Suggestions are a five-item shortcut, never a catalog or a second editor; search and filters live only in the library browser. The selected starting point is summarized on the form and can be removed before continuing. Suggestions and the library use one discovery source and the same card.

The existing contracts create/copy a private draft with provenance, customize it, publish a private snapshot, and enroll that version. `Add to Calendar` performs the private publish and enrollment in sequence; show errors and allow retry if one succeeds without the other. Never change the source Program's visibility or content.

- The Program cover uses the shared media tray (`04-UI.md` §4a): one preview tile with inline remove and one add/replace tile, no separate upload or library buttons. It sits on the Details step; it is not a hero.

- Frequency and duration belong to each Activity (07 §7, 08 §2): every Activity row, and the inline New Activity form, has its own frequency and duration controls. Program duration is chosen on Details.

- Program detail (`/programs/:id`) may offer its owner the same controls inline (details, cover, duration, visibility, Activity rows). It reuses the Workspace's components and does not replace the Workspace.
- Do **not** add an 8-item setup grid or separate Pricing/Calendar steps to the Workspace.

## 5. Calendar: first-stop daily experience

Top: month heading/navigation; controls `+ Program`, `+ Activity`; user avatar with unread badge. Default shows the **current month** with today highlighted, in the user's timezone; day, week, and year views are one button away. Activity tiles show thumbnail/icon, title, optional origin Program, Day-view local time if set, collaborator avatar(s) or unread indicator when meaningful, and quiet visual completion styling (no visible status badges or `"More actions"` overflow menus; do not reintroduce them in future refactors). A tap opens the **dated occurrence**, not the reusable Activity editor. Choosing a date in Week, Month or Year opens Day view for that date; today is marked with `aria-current="date"` and a distinct style whether or not it is selected.

**First use:** an empty week, one line `Nothing scheduled this week`, a prominent `Browse Programs`, and a secondary `Add Activity`. Any later empty week or day uses the same copy and actions.

**Add Program:** browse/preview → (Unlock if needed) → `Start Program`, which schedules the Program from today in one action and stays on the Program page (`13` §4). `Start Program` itself has no date picker, preview, confirmation or reminder prompt; the secondary **Add to Schedule** opens the shared dialog to choose another start date (§2a, `13` §4). A group invitation's start date still applies. **Add Activity:** picker → select target date/time (default current selected date; time optional) → `Does not repeat` by default, or Daily/Weekdays/Weekly/Custom → confirm.

**Adjusting:** a tile's time can be changed inline in Day view, clearing it moves the item to Any time, and items can be dragged between hourly/Any time slots; preserve user-specific adjustments. Individual Calendar tiles omit overflow menus (`More actions` / `Remove from Calendar`); Program-level removal (`Remove from Calendar`) lives on Program Detail, while individual item cancellation APIs remain preserved underneath.

**Selected Activity panel (2026-11-15):** Day and Month share one selection and one panel (a bottom sheet below `lg`). Selecting a Day chip or a Month tile opens it in place, without navigating or switching views; selecting in Month also moves the selected date to that entry, so the selection holds across Day ↔ Month while the entry stays in range. Month is a planning surface: every cell has one fixed height, so rows never jump as entries move or overflow opens, and Today's date is a filled accent circle and the selected date an accent ring.

**Geometry (2026-11-16):** spacious and precise rather than compact; vertical scrolling is preferred to shrinking. Month cells are 216px tall with 12px padding and subtle grid lines, with a 28px date header row (its date mark has a 44px hit area). Activity cards are 44px small scheduled cards: the time (and any overlap mark) on a small first line and the title on the second, with an untimed title using both lines. A cell shows as many cards as its geometry holds: all when they fit (three), otherwise two beside `+N more` (one source, `lib/calendarGeometry`). An empty date shows a quiet "+ Add" on hover. Day hour rows are 96px (88px on phones), the time column about 80px, and cards 44px. The sidebar is 352px: docked in Day from 1024px and in Month from 1440px. In Month at 1280–1439px it is a drawer over the page edge, so the seven columns keep their full width; it steps aside while dragging, returns if the drag is cancelled, and stays collapsed after a successful move (selection kept) until an entry is chosen again. While dragging, `+N more` and quick-add layers close so they never cover a drop target. The 44px toolbar, the phone/tablet date strip and its 44px targets are unchanged; no width scrolls horizontally.

**Series in the panel (2026-11-16):** a repeating entry's panel shows its rule and end in words ("Every week on Mon, Wed · until Dec 14") with **Edit series** and **End series**, both from that entry's date on (This and future, 09 §4.8). Edit chooses Daily, Weekdays, Weekly (days), Every few days or Monthly, an optional time and Ongoing / Until a date, with a one-line summary, through `updateCalendarRecurrence`. End removes planned entries from that date through `endCalendarRecurrence`. Earlier entries, completions and results never change, and entries the person moved keep their date.

**Conflicts in Month and the panel (2026-11-16):** timed entries the server marks as overlapping show a small attention mark on their Month chip and Day badge (also announced: "overlaps another Activity"). The panel adds "Overlaps another Activity at <time>" with **Move to next open slot**, the existing `moveCalendarItemToOpenSlot` (the next free half hour that day until 10 PM, else the next day). Only that entry moves, also for a series; a gathering entry confirms leaving first; the toast offers Undo.

**Direct scheduling (2026-11-16; replaces Month drag-and-drop of 2026-11-15):** Calendar entries move by direct manipulation with mouse and touch in Day and Month, through one shared drag system.
- **Start.** With a mouse, dragging starts after a few pixels, so a click still selects. With touch, a long-press (about a third of a second) starts it, so a tap still selects and a swipe still scrolls. Only open entries (planned or not participating, not locked) drag; completed, skipped and locked ones do not, and say why.
- **During.** The entry floats under the finger or pointer while the original stays faded in place, so grids never reflow. Valid targets highlight (a Month cell shows "Move here · <time>"); refused ones show not-allowed. The page auto-scrolls at its edges.
- **Targets.** A Month cell or a date in the phone/tablet date strip changes the date and keeps the time. A Day hour row sets that hour (`HH:00`); the Any time row clears the time. Leading and trailing adjacent-month days are loaded, shown faded and accept drops. Dates before today, and a drop that would change nothing, are refused.
- **Cancelling.** Escape, lifting outside a valid target, or ending a touch without a long-press changes nothing. Nothing is written until a valid drop. Dragging never starts, completes, duplicates or enrolls anything, and the click that ends a drag is swallowed.
- **Writing.** A one-off moves at once, shows at its new place immediately and offers `Undo`, which puts the same entry back. A failed or stale write puts it back, explains why in one toast and reloads the Calendar. A recurring entry asks `This one` (default) / `This and future` first (09 §4.8); This and future moves the rest of the series by the same number of days, or gives them the new time, and has no Undo. A gathering entry confirms that moving leaves the gathering (10 §9.6). Cancel in either dialog writes nothing. Everything uses `updateCalendarItem` (`localDate`, `localTime`, `scope`, `expectedUpdatedAt`); there is no separate move operation.
- **Offline.** Nothing drags while offline.
- **Alternatives.** The panel's **Move to date** opens the shared Reschedule dialog (date and time; the keyboard and assistive-technology path), and screen readers hear pick-up, hover and drop announcements.
- **Quick add.** Clicking an empty spot in a Month date, or its `+`, opens the Activity picker for that date (today or later); Day keeps adding from any hour or Any time row.

**Preferences (2026-11-15):** Day/Month, the Activity filter and Focused Hours / All 24h are remembered per user in this browser (local storage, never account settings). An explicit `view` in the URL, as in a shared link, overrides the stored view. Panel order: title (to the Activity page), date · time · duration, one image (resolved media, else the category fallback), a short description with steps one tap away, participation (§2b; a group session adds its own count), then actions: Mark as Complete / Undo, Start or Resume, and **Remove from Calendar**. Removal confirms in a compact dialog (`This one` / `This and future` for a recurring entry), cancels the entry only (09 §4.8), never completes it or deletes the Activity, and is unavailable on a completed entry until Undo. A `This one` removal offers `Undo` in its toast, which restores the same entry (status back to planned, same date and time; a gathering is not rejoined); removing `This and future` has no Undo. Day view All 24h opens at the earliest of 6 AM, the first entry and the current hour; earlier hours fold into one row.

**Conflicts:** overlapping Activities are allowed. Timed items at the same local time are marked on both tiles, with one-tap `Move` offering the next open slot. Never block scheduling.

**Responsive:** desktop has the week grid + optional side panel; mobile shows a week strip above the selected day's list and a detail sheet.

**Controls (2026-11-15):** one row at every width: the date title (opens the date picker), `Today`, and one `View` button whose menu holds Day/Month, Focused Hours/All 24h (Day view) and the Activity filter; a dot on `View` marks an active filter. On mobile there are no Previous/Next buttons; the date picker moves between dates. Desktop keeps Previous/Next beside the title. Keyboard alternative for all drag actions (Move button with date dialog).

Timed ready Activities lead with Start, simple Activities with Complete; active shows Complete and Pause, paused leads with Resume, completed offers Undo completion. 3. **My Metrics:** configured result inputs and real personal statistics (completion counts, streaks or progress only when supplied). Never prefill recorded values from targets. Omit it if there are neither inputs nor statistics. *(Approved 2026-11-10: these render inside the Today section, after its statistics and before the instructions, rather than as a separate row.)*
4. **Together:** actual group avatars, permitted completion states, recent shared completions/starts, reactions and group access. No inferred live presence or claims about private members. Group occurrence identity remains authoritative across Program versions. Omit for solo Activities.

No Media Library workflow or dedicated History section; preserve historical records and server authorization.


Instruction text is **embedded**, and instruction media appears in Related Media: 1 instruction with a primary video surfaces naturally as helpful thumbnail/inline selected content; multiple instructions accessible by swiping/next or expanding within the activity, no obligatory “Read instructions” screen. These rows are the whole page; do not add, reorder, or tab them. The one addition is an optional privacy-safe community aggregate line after Related Media, shown only when the server supplies it. Do not force media into a huge hero by default; user results and completion remain first. Photo/video is optional and not a prerequisite to `Finish`.

### Session state interaction

`READY -> ACTIVE -> PAUSED -> ACTIVE`, `ACTIVE|PAUSED -> FINISHED`, optional `ABANDONED` with confirmation. `Finish` records effective active time, never pause time, saves pending results, and **returns to the same calendar week and date** with completion visible and `Undo` available. Reopening a finished occurrence shows its completed status and `Undo completion`. Starting does not automatically mark Activity complete; completion is explicit. If the user completes without starting, offer quick `Mark finished` with explicit result saved as manual duration/unknown time rather than synthesizing a measured duration. Restart after Finished should create a **new session attempt**, not erase history.

### Metrics controls

Use compact `− value +` for counts, one-tap `Start Timer` for duration, toggles for yes/no, text only for notes or custom inputs. Prefill *suggested target*, never silently copy it into actual result as verified. If result was modified, saving is immediate/explicit by stable affordance; undo available. Show unit and metric label. Do not show irrelevant metrics.

## 7. Activity and Instruction Builder

**Add Activity is one create-or-start experience**, not a suggestion catalog with creation hidden behind it. Lead with the user's own Activity title and the minimum required classification. Summary and instructions are optional. Keep the primary action available for a new Activity without requiring a suggestion selection. Existing Activities are optional starting points: up to five suggestions and a `Browse Activity Library` action that opens the shared library browser (see `08-ACTIVITIES.md` §6).

Use the same Activity basics form in both Calendar and Program contexts: title, category, optional summary, and optional instruction. Continue in context: create a private Activity and place it on the chosen Calendar date, or create it and add it to the current Program. Creation and placement errors remain visible, preserve entered content, and allow retry. The Calendar retains its selected date and return destination.

After the basics, offer `+ Media` / `+ Metrics` / `+ Tools` / `+ Instruction` as optional enrichment. Save Private is the default; Publish is separate and deliberate. A user can create an Activity with only a title and category, then enrich it later.

**Instruction mini-builder:** (1) brief guidance/name → (2) optionally attach media/metrics/tools with same controls → (3) Done/Add another. Reusable component patterns; no forced 14-step flow. A one-instruction Activity can be effectively a video; no extra navigation for basic playback. Instructions are ordered, without recursively nested instructions.

**Customizing:** Select seeded/public Activity → `Use as is` or `Customize Copy`; attempting to edit an Activity you do not own always creates a personal copy. The copy starts private with source attribution; the original never changes. Return to the original Program with the selected activity placed.

## 8. Media Studio and engagement

Entry button `Add Media` opens three broad actions: `Library`, `Upload`, `Record`. Library distinguishes **My Media** and **Platform Library** without separate mandatory tabs; search and filters are available. Record: camera preview, context-specific prompt, record, review/retake, choose audience; save **Private** by default; return to originating item. Camera/mic consent only on start; if denied, offer `Upload instead`.

Media viewer: tap thumb → play → swipe/next or desktop arrows → creator credit. Public media shows compact like/view metadata. Group-shared media shows its comments. The currently selected Program creator's eligible instructional media sorts first. Comments exist only on group-shared media in P1.

## 9. Collaboration behavior

In solo activity, hide collaboration rows. Group activity row shows members, statuses, and completion reactions. Finishing an item shares only the approved completion signal under group policy; never implicitly shares exact measurements or media. Joining a group states plainly that completion will be visible to members and that this can be turned off. Reactions target permitted completion events. Comments target group-shared media. There is no general chat and no `Live` control in P1.

## 9a. Reminders and achievements

**Reminders:** in-app notifications are on by default. The daily email is optional, off until the user opts in, sent at their chosen local time (default 08:00), and only on days with planned items. Every email has a one-click unsubscribe.

**Achievements:** earned quietly from actual completions and shown on the Finish return as a small confirmation, then on the user's profile. They are private until the user shares them. Never use guilt, streak, or comparison language.

## 11. Accessibility and mobile-first requirements

Minimum 44px touch targets for primary actions; meaningful focus outlines; visible labels for icon-only controls on hover/assistive tech; keyboard-operable grid/carousel/calendar; screen reader announcements for recording/session state and saved metrics; caption/transcript support for instructional video; do not autoplay with sound; respect reduced-motion; sufficient contrast; avoid public health/body comparisons or guilt-based copy.

## 12. Handoff checklist

Each implemented page must specify: entry action, origin context, main action, returned destination, empty/loading/error states, privacy gate, keyboard/mobile path. Screens must never invent additional persistent data fields without an authoritative domain contract.
